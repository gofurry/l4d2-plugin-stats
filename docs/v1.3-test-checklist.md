# v1.3.0 测试与验收清单

本清单验收 Collector/Dashboard `1.3.0`、Stats schema 4、Dashboard schema 13、Incident Contract v1、Round Context Contract v1，以及保持不变的 `stats_version=1` 和 Aggregate Contract v1。

## 升级与静态检查

1. 停止 Dashboard，执行 `l4d2-stats backup create --config ./config.yaml`；MySQL/PostgreSQL Stats DB 另用原生工具备份。
2. 同时部署 `.smx` 和三种驱动的全部迁移；不要只替换插件。
3. 仓库根目录执行：

```powershell
python scripts/test_sqlite_migration.py
python scripts/validate_versus_contract.py
python scripts/validate_analysis_contract.py
powershell -ExecutionPolicy Bypass -File scripts/validate-migrations.ps1
powershell -ExecutionPolicy Bypass -File scripts/build.ps1
```

4. `dashboard` 执行 `gofmt` 检查、`go vet ./...`、`go test ./...`、`go tool sqlc generate` 并确认生成代码无差异。
5. `dashboard/frontend` 执行 `pnpm test`、`pnpm typecheck`、`pnpm lint`、`pnpm build`。
6. SQLite 契约测试应在本地通过；MySQL 8.4/PostgreSQL 17 由 `database-contract.yml` 使用相同 fixture 验证。

## Collector 与数据库

1. `sm_lps_status` 显示 `version=1.3.0`、`state=ready`、`schema=4/4`，并包含 Analysis 队列、expected/dropped 与最近错误状态。
2. `lps_schema_migrations` 包含 1–4；`lps_round_contexts`、`lps_incidents` 及规定索引存在。
3. 在 `coop`、`realism`、`versus` 各完成至少一个真人参与的 Round；每个 Round 至多一条 Context，模式/服务器/规则字段正确。
4. Round 中改动 tracked CVar 后 `change_mask` 对应 bit 永久置位；改回原值也不清除。缺失可选 CVar 使用空字符串或 `-1`，不使插件失败。
5. 分别触发控制及解除、倒地、死亡、普通救援、挂边救援、除颤、警报车、Tank/Witch 出生与死亡；类型、参与者、相对时间、控制时长/end reason 和 Boss 关联符合契约。
6. 纯 Bot 对 Bot 不入库；有认证真人参与时允许保存 Bot 参与者；Witch 不采集 Startle。
7. 正常结束且无丢失的 Round 为 `capture_complete=1`；禁用、队列溢出或故障 Round 不得伪装成完整零事件样本。
8. 人工使 Analysis SQL 失败时核心 Session/Segment/PvE/Versus 快照仍成功；恢复后队列按每次最多 256 条重试，重复写不产生重复行。

## Dashboard 公共页面

1. `l4d2-stats version` 输出 `1.3.0`；Dashboard 自动迁移至 schema 13，ready health 显示 Stats schema 4。
2. `/analysis` 只有“地图与战役”“规则环境”两页签；默认 90 天、全部服务器、PvE、全部战役，并可切换 30/90/180 天/全部、服务器、模式和战役。
3. “地图与战役”和“规则环境”使用服务端分页；地图、对局数、通关率、平均尝试、时长及每场完整对局事件指标均可按后端结果升降序排列。
4. PvE 完成率只使用 `completed + failed`；无玩家 Segment 的 Round 被排除。Versus 不显示伪 PvE 完成难度。
5. Incident 指标只使用 enabled/complete/zero-dropped Round；页面显示统计日期与战局明细完整率。60 秒时间线使用“每 100 个到达该桶的 Round”分母。
6. 地图详情的事件构成、Tank/Witch 匹配生存时间正确；未匹配 Death 只计死亡数，不进时长样本；页面不渲染伪坐标热力图。
7. 规则环境只把 `change_mask=0` 纳入稳定 fingerprint 分组；字段和 `ctx-xxxxxxxxxxxx` 指纹可核对。
8. 个人页“分析”标签显示 PvE/对抗幸存者/感染者派生指标、样本门槛、最近战局统计和双控/三控/四控；不足样本显示不可用而非 0。
9. 首页和管理后台的玩家预览都显示同 Round、同阵营、正重叠 Top 3“并肩作战”；无数据时状态一致，且不暴露 peer SteamID。
10. 首页优先显示 schema 13 保存的最近成功 A2S 状态并后台刷新；首次没有快照时显示查服进度，查询失败后仍可保留旧快照。

## 排行榜、保留与诊断

1. 每小时榜至少 7200 秒，Boss 参与率至少 5 次遭遇，每出生榜至少 20 次出生；低值优先榜按升序并返回 `lower_is_better=true`。
2. Context 不进入 Aggregate v1 维度；v1 既有榜单统计语义不变。
3. 管理页显示 Context/Incident 行数、完整/丢失 Round、可用窗口、日增长和保留投影；Incident 默认保留 180 天。
4. Incident 清理只删除已结束 Round 的过期 v1 行，每批最多 500；预览/确认/审计独立，发现未知版本时拒绝删除。
5. `doctor --deep` 对健康数据无 error；构造未知版本、非法 kind/reason/flags、负时长、完整性计数错误和失配 Boss 关联时完整报告 error。
6. 备份/恢复、诊断脱敏、既有聚合和原始数据清理回归通过。

## 性能与回滚

1. 用中型/大型 fixture 记录 SQLite 查询计划和写锁、MySQL/PostgreSQL 批量插入、分析 API/并肩作战 P50/P95/P99、2048 队列恢复和增长量；不把“每 Incident 字节数”写成契约。
2. 升级前验证旧 Collector/Dashboard 对 schema 4 的行为。无法证明单二进制回退安全时，按保守边界同时恢复 v1.2 二进制与升级前 Stats/Dashboard DB。
3. 历史 v1.2 数据仍应显示核心统计与并肩作战；历史 Context/Incident 明确显示不可用，不得补零。
